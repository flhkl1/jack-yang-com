Problem

Capacity requests on a large ML platform were resolved by hand, often by combing through dense logs and ticket information.

User

Oncall SWEs at AWS

System

Click a box.

Ticketee

Where an on-call engineer files and works a capacity ticket. The agent’s diagnosis shows up as a comment on the ticket.

Try the rebuild

Web frontend

A chat view of the same agent: streamed replies, saved instructions, themes, and buttons that suggest the next action.

Capacity agent · Claude Opus

Every new ticket fires an EventBridge trigger that hands it to the agent. The agent adds a first diagnosis to the ticket and suggests a change.

It never applies a change alone. A person approves every one.

Real-time data MCP

Read-only. Answers questions about capacity right now.

Ticketee MCP

Reads tickets and writes comments back. It can search past tickets by resolution, on-call engineer, category or severity, so you can ask in plain English how tickets like this one were solved.

Before it, there was no way to look up how earlier tickets had been resolved.

Offline data MCP

Read-only. Answers questions about history.

Execution MCP

Applies a capacity change once a person has approved it.

Live capacity metrics

Current capacity, as it changes.

Ticket queue

Every capacity ticket and its comments. Ticketee and the Ticketee MCP work on the same queue, which is what closes the loop.

Data lake

Structured time-series data on users and their capacity usage.

My part

The Ticketee MCP, the Ticketee frontend, and parts of the backend, including the trigger that hands each new ticket to the agent.

Result

  • P99 time from ticket created to resolved down 94%.
  • Used by 60+ engineers, through both frontends.
